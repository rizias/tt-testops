# AGENTS.md

`tt-testops` — читающий шлюз к Allure TestOps: тянет тест-кейсы, рендерит их в Markdown или HTML и
ставит пометки о состоянии кейса. Командная строка в npm-пакете. Как пользоваться —
в `README.md`; здесь — как менять.

## Команды

- `npm install` — зависимости.
- `npm run check` — сборка, типы, линт (включая размер файлов), knip, тесты. Единственная мера готовности;
  запускай перед коммитом и перед публикацией.
- `npm run build` — `tsc -p tsconfig.build.json` → `dist/`.
- `npx lefthook install` — git-хуки: перед коммитом линтер по застейдженным файлам, размер файлов и
  секреты; перед отправкой — `npm run check`.
- `openspec list` — способности и активные изменения.
- `openspec validate <имя> --strict` — проверка изменения.
- `npx vitest run <файл>` — один файл тестов, когда чинишь конкретное падение.
- `vitest.config.ts`: файлы тестов, запускающие процесс CLI, перечислены в `processTests` и идут друг за
  другом, остальные — параллельно. Новый тест с запуском процесса добавляй в этот список, иначе он будет
  случайно падать по времени под нагрузкой соседей.

## Порядок работы

- Источник истины — `openspec/specs/`. Восемь способностей: `testops-access`, `case-model`,
  `case-rendering`, `quality-marks`, `cli`, `html-view`, `attachments`, `distribution`.
- Любое изменение начинается с предложения, не с кода: `openspec new change "<имя>"` → предложение →
  спецификации → design → задачи → код.
- Меняется поведение — сначала требование в спецификации, потом код, потом версия пакета. Поведение
  прежнее — зелёная `npm run check`, и всё.
- Поведение — то, что видно через публичный контракт: команды, вывод, коды выхода, записанные файлы.
  Что считать изменением поведения, решает владелец.
- Уточняешь существующую обязанность — правь то же требование (`MODIFIED`), а не пиши новое рядом.
- Обоснование решения пиши в `design.md` изменения. Память агентов хранилищем решений не является.
- Непонятно — спроси владельца и жди ответа. Найденный по ходу дефект — вопрос, а не разрешение чинить.
- Черновики, сырой анализ и прототипы — в `.internal/`, вне гита.

## Стиль кода

- TypeScript, ESM, Node 22+. Линт — ESLint, форматера нет.
- Комментариев в коде нет: ни однострочных, ни блочных, ни JSDoc. Исключения — shebang, директивы
  инструментов и маркер `owner:` по прямой просьбе владельца. Проверяет правило `local/no-comments` из
  `eslint.config.js`; директивы `eslint-disable` запрещены. Непонятный код переписывай, а не
  комментируй.
- Функция сложнее 15 по правилу `complexity` — ошибка; подавлений нет: файла `eslint-suppressions.json` нет,
  директивы ESLint в коде запрещены.
- Файл `.ts` — не больше 300 строк. Больше — в нём несколько ответственностей; дели по ответственности,
  а не по строкам. Проверяет правило ESLint `max-lines`: 300 строк для кода, 500 для тестов.
- Минимум кода: YAGNI, stdlib до зависимостей, никаких абстракций с одной реализацией, ничего «на
  будущее». Не упрощай только проверки на границах доверия, защиту от потери данных и безопасность.
- Мёртвого кода нет: объявленное либо используется, либо удаляется; `knip` в `npm run check` это
  проверяет. Настройка без поведения — дефект.
- Никаких временных решений, заглушек и фиктивных успехов.
- Ядро не пишет в стандартный вывод; сообщения — в служебный вывод (stderr).
- Документы, сообщения об ошибках и вывод — на русском; технические термины — по-английски.

## Тестирование

- Проверяй только через наблюдаемые границы: команды и коды выхода, Markdown побайтно,
  самодостаточная HTML-страница, запросы через подменяемый `TestOpsPort`.
- Тест вне этого списка — вопрос владельцу, а не твоё решение.
- Порядок: требование в спецификации → код → тест на изменённую границу.
- Красных тестов не бывает: `skip`, `pending` и пустой тест — красные.
- Ожидаемое значение бери из независимого источника, а не пересчитывай формулой из кода.
- Называй файл теста по предмету проверки.
- `npm run check` собирает `dist/` до тестов; тест командной строки запускает собранный `dist/cli.js`.
- К боевому серверу TestOps не обращайся ни одним запросом: сеть подменяется целиком.

## Контракты вывода

- Markdown: стандартный CommonMark, жирные звёздочки в шапке, литерал `Нет шагов`, вложенность шагов
  отступом; кейсы в пачке идут подряд, каждый с шапки. Список — в способности `case-rendering`.
- Источник истины — структурный `TestCase`. Markdown и HTML строятся из него.
  Разбирать Markdown обратно внутри шлюза запрещено.
- Golden-тесты — основной шлюз качества.

## Архитектура

Data-пайплайн, не гексагон: `fetch → normalize → TestCase → пометки → render(FormatProfile) → Markdown или HTML`.
Пометки считает отдельный модуль. Рендерер читает профиль формата; обход шагов и определение формата
остаются в коде. Раскладка плоская — один файл на роль:

```
src/
  cli.ts              командная строка: разбор и таблица команд; args.ts — флаги, querySources.ts — запросы и ссылки в источники, usage.ts — справка
  caseCommand.ts      команды case и attachments; listCommand.ts — list, link и справочники
  output.ts           вывод результата на экран или в файл, строка об окончании
  catalogCommands.ts  команды справочников: fields, trees, projects, count
  localCommands.ts    команды без сервера: setup, init, update, config, attachments и attachments clear
  skills/setup.ts     init, update, синхронизация копий скилла; updater*.ts — реестр копий и их обновление
  gateway.ts          оркестрация: получить → нормализовать → отрендерить; gatewayCatalog.ts — справочники, число кейсов и ссылка
  caseFetcher.ts      сбор кейсов по источникам: поиск, идентификаторы, хранилище
  reference.ts        справочник проекта: поля, слои, поиск значения по тексту
  emptyResult.ts      пустой ответ: исправление написания или ошибка со списком
  queryCheck.ts       разбор условий запроса, похожесть написания
  assets.ts           встраивание вложений в страницу
  attachmentFiles.ts  вложения кейса файлами на диск
  config.ts           сборка AppConfig из выбранного профиля и окружения
  settingsPaths.ts    каталог состояния, выбор профиля и его источник
  settingsSchema.ts   поля настроек, их переменные, типы и умолчания — одна таблица
  configCommand.ts    команда config: просмотр настроек, init, use, profiles
  stateLock.ts        межпроцессная блокировка и атомарная запись в каталоге состояния
  attachmentStore.ts  хранилище профиля: вложения по кейсам, сессии, деревья; очистка
  sessionStore.ts     сессия доступа в хранилище: замок, атомарная запись
  profile.ts          FormatProfile: оформление вывода; profileCheck.ts — его проверка
  model.ts            RawCase, TestCase, Scenario, ScenarioStep
  normalize.ts        сырой ответ → TestCase; tree.ts — путь из рабочего дерева
  scenarioSource.ts   где лежит сценарий и откуда его брать — одно решение; runScenario.ts — шаги из тестового результата
  treeResolver.ts     выбор рабочего дерева проекта и его хранение
  stepBuilder.ts      шаги нового редактора → модель сценария; scenarioMarkdown.ts — модель → строки Markdown
  contentResolver.ts  скачивание вложений, абсолютизация картинок; inlineContent.ts — вложения шага старого формата
  render.ts           TestCase → Markdown
  html.ts             страница и дерево разделов; htmlCase.ts — кейс
  htmlText.ts         текст шага; htmlRich.ts — разметка; htmlRichSteps.ts — сценарий из модели
  htmlStyle.ts        вид; htmlScript.ts — поведение; htmlLayoutStyle.ts, htmlGutter.ts — колонки
  audit.ts            пометки о состоянии кейса
  text.ts             нормализация текста, обработка ссылок
  report.ts           имя файла выгрузки и строка об окончании
  links.ts            разбор ссылки на фильтр TestOps; sources.ts — источники запроса
  setup.ts            совет команды setup: как поставить инструмент в проект
  errors.ts           типы ошибок
  testops/client.ts   кейсы, проекты, деревья; search.ts — постраничный поиск
  testops/attachments.ts  вложения; fields.ts — поля и значения
  testops/catalog.ts      проекты, деревья, слои
  testops/diagnosis.ts    разбор отвергнутого запроса; http.ts — ошибки ответа
  testops/port.ts     интерфейс клиента для подмены в тестах
  testops/session.ts  обмен токена на JWT и переиспользование сессии
test/                 снимки вывода и round-trip-проверки
```

- `contentResolver` — самостоятельная стадия конвейера, а не помощник рендера.
- Модель сценария (`Scenario`, `ScenarioStep` в `model.ts`) явно выражает общие шаги, оба формата ожидаемого
  результата и опускание заголовков. Markdown и HTML строятся из неё; разбирать строки одного вывода ради
  другого запрещено.
- `FormatProfile` покрывает только оформление. Поля AQL, карта проектов и таймауты живут в `AppConfig`;
  пути эндпоинтов — константы в коде.

## Коммиты и pull request

- Перед коммитом — зелёная `npm run check`.
- Сообщение коммита — одна строка по существу. Не перечисляй файлы и не пересказывай дифф: это видно в
  самом коммите. Описание pull request — по тому же правилу.
- Требования и код — разными коммитами, требования первыми. Один коммит на оба — порядок не доказан.
- Никаких следов ассистента: ни соавторства, ни упоминаний модели — ни в коммитах, ни в PR, ни в коде.
- Публикация пакета — только по явной команде владельца.

## Выпуск

- Перед выпуском раздел «Не выпущено» в `CHANGELOG.md` заполнен: пустой раздел останавливает выпуск.
- GitHub → вкладка Actions → Release → Run workflow → `patch`, `minor` или `major`. Дальше ручных шагов нет.
- Workflow сам гоняет `npm run check`, выполняет `npm version` (хуки переносят «Не выпущено» в раздел
  версии и ставят версию в шапку скилла), отправляет коммит с тегом, публикует пакет в npm и создаёт
  запись `vX.Y.Z` на странице GitHub Releases с текстом раздела.
- Публикация в npm — доверенная, через OIDC, без токена. Разовая настройка на npmjs.com: карточка пакета
  → Settings → Trusted Publisher → GitHub Actions, владелец `rizias`, репозиторий `tt-testops`, workflow
  `release.yml`.
- Выпуск упал после публикации — перезапуск запись в Releases не восстановит:
  `gh release create vX.Y.Z --verify-tag --title vX.Y.Z --notes-file <файл с текстом раздела>`.

## Безопасность и данные

- Только чтение. Продукт не пишет в TestOps ничем и никогда.
- Никаких личных и проектных данных в репозитории: ни адресов серверов, ни номеров и имён проектов, ни
  идентификаторов кейсов, ни имён полей и их значений, ни счётчиков. В примерах — плейсхолдеры:
  `<ид>`, `cf["<Поле>"]`, `<Значение>`.
- Секреты живут в `credentials.json` профиля и переменных окружения, в гит не идут. Ни API-токен, ни выданный сервером
  JWT не попадают в вывод команд, в служебный вывод и в сообщения об ошибках.
- К боевому серверу владельца не обращайся без явного разрешения — даже читающим запросом.

## Отчёты

- Вывод не шире проверки: проверил одного — не пиши «эти»; не измерял — не называй числом.
- Каждое утверждение сопровождай командой и её выводом. Отчёт субагента или воркера — гипотеза, пока не
  прогнал проверку сам.
- Сначала суть, потом подробности. Номера пунктов спецификаций не приводи.
