# tt-testops

Читающий шлюз к Allure TestOps. Всё делается командой `tt-testops`.

## Запреты

- **Не ходи в API TestOps сам**: не составляй HTTP-запросы, не бери токен из `credentials.json` и переменных окружения, не подбирай эндпоинты.
- **Не перебирай команды наугад.** Один `fields --find` отвечает, где лежит слово; не вызывай `fields <имя>` по каждому полю.
- **Не решай за человека.** Сказанное можно понять двумя способами — покажи варианты с числом кейсов и спроси.
- **Нужной возможности нет** — скажи об этом человеку. Это заявка на доработку, а не повод лезть в API.

## Команды

| Команда | Когда |
|---|---|
| `tt-testops case <id>` | один кейс |
| `tt-testops list <запрос>` | все кейсы по запросу |
| `tt-testops count <запрос>` | сколько кейсов подходит — одно число, кейсы не качаются |
| `tt-testops fields` | обзор проекта: поля с числом значений, слои с числом кейсов |
| `tt-testops fields <имя поля>` | значения поля с числом кейсов; `layer` — слои |
| `tt-testops fields --find <текст>` | где встречается слово — готовыми условиями запроса |
| `tt-testops link <запрос>` | ссылка на фильтр TestOps для человека |
| `tt-testops projects` | список проектов и что есть на сервере сверх него |
| `tt-testops trees` | деревья разделов проекта и какое рабочее |
| `tt-testops attachments` | хранилище вложений профиля; `attachments clear` — очистить |
| `tt-testops case <id> --format raw` | сырой ответ сервера, когда надо понять, что пришло |
| `tt-testops setup [путь]` | как подключить инструмент к проекту; ничего не меняет |
| `tt-testops config` | текущие настройки: профиль, пути, значения и их источник |
| `tt-testops init [путь]` | разложить этот скилл в проект; `--for claude,agents` — без вопроса |
| `tt-testops update` | обновить пакет до последней опубликованной версии |

Флаги: `--profile <профиль>` и `--out <файл>` — у всех команд. Остальные — по командам: `case` — `--format markdown|html|raw`, `--no-marks`, `--tree`; `list` — `--format markdown|html`, `--no-marks`, `--tree <название|none>`, `--project <id|имя>`, `--limit N`, `--rql`, `--rql-file`, `--text <фраза>`; `count` и `link` — `--project`, `--rql`, `--rql-file`, `--text`; `fields` — `--project`, `--find <текст>`; `trees` — `--project`; `init` — `--for`. Флаг не той команды и незнакомый флаг — ошибка, команда не выполняется.

## Просьба человека → один запрос

«Найди end-to-end тесты по такому-то разделу» разбирается на условия:

1. **Слой** — вид тестирования (e2e, UI, API, юнит, чеклист): `layer = "E2E"`. Какие есть — `fields layer`.
2. **Раздел, модуль, эпик, функционал** — значение кастомного поля. Где оно живёт — `fields --find <слово>`, он вернёт готовое `cf["<Поле>"] = "<Значение>"` с числом кейсов.
3. **Часть названия кейса** — `name ~= "<слово>"`.
4. **Фраза из текста кейса** — шаг, описание: `--text "<фраза>"`, как «Содержимое» в поиске TestOps; сочетается с условиями выше.

```bash
tt-testops count 'layer = "E2E" and cf["<Поле>"] = "<Значение>"' --project <ид>   # сначала объём
tt-testops list  'layer = "E2E" and cf["<Поле>"] = "<Значение>"' --project <ид>
```

Запрос с опечаткой инструмент не исправляет: при пустом ответе он называет в ошибке несуществующее поле, значение или слой и похожие написания из справочника.

## AQL

`<запрос>` — AQL либо ссылка на фильтр TestOps целиком; ссылку бери в одинарные кавычки, иначе `&` разорвёт команду. Ссылка принимается с любыми условиями интерфейса TestOps — тегами, кастомными полями, содержимым, сохранённым фильтром (`filterId`); всё это уходит на сервер как есть. Ссылка без единого условия и без `filterId` — ошибка.

Отбор по содержимому кейса (условие «Содержимое» в TestOps) — флаг `--text "<фраза>"` у `list`, `count` и `link`. Сочетается с AQL и со ссылкой; без запроса — поиск по фразе среди всех кейсов проекта; пустая фраза — ошибка.

- кастомные поля **только** как `cf["Имя"]`, по ним работает точное `=`;
- слой — `layer = "..."` или `in [...]`, подстрока не поддерживается;
- `automation = true|false`;
- операторы `=`, `!=`, `~=` (содержит — для `tag` и `name`), `in [...]`, `not`, `is null`, `>`, `<`, `>=`, `<=`; условия соединяются `and` / `or`, `and` сильнее.

Ошибся в синтаксисе — инструмент печатает операторы и реальные поля проекта. Читай сообщение, в нём ответ.

**PowerShell 5.1 съедает вложенные `"`.** Признак — «Проектов 1, а запросов 2» или `400` на верный запрос.
В PowerShell экранируй внутренние кавычки: `'cf[\"<Поле>\"] = \"<Значение>\"'`, либо положи запрос в файл и
передай `--rql-file <файл>` — так надёжнее. В bash одинарных кавычек снаружи достаточно.

**«Не нашлось» и «сломано» — разное.** На опечатку TestOps отвечает нулём кейсов. При пустом ответе инструмент сверяет написанное со справочником: чего нет в проекте — ошибка с похожими написаниями и списком доступных. Сказано «кейсов не найдено» без пояснений — выборка честно пуста.

## Несколько проектов одним вызовом (`list`, `count`)

```bash
tt-testops list --project <ид-2> --rql 'cf["<Поле-2>"] = "Раздел Б"' \
                --project <ид> --rql 'cf["<Поле-1>"] = "Раздел А"' --format html
tt-testops list 'automation = false' --project <ид-1> --project <ид-2>
```

Запрос относится к ближайшему `--project` слева; один запрос раздаётся всем проектам; количества не сошлись — отказ. `--limit` считается на каждый проект. `link` на несколько пар откажется.

`id in [...]` проектом не ограничен — кейсы берутся из своих проектов; любое добавочное условие возвращает запрос в границы проекта.

## Путь кейса

Путь — уровни дерева разделов. Деревьев бывает несколько; какое рабочее, знает человек: поле `trees` файла `profile.json` (`{"<ид>": "<название дерева>"}`, `none` — путь не нужен) или флаг `--tree` на один вызов. Дерево называется **названием** — тем же, что человек видит в интерфейсе TestOps: `--tree "<название>"`, `"trees": { "<ид>": "<название>" }`; идентификаторы человеку не показывай. Деревьев несколько, а выбора нет, либо названного дерева у проекта нет — `case` и `list` останавливаются с кодом 1 до выгрузки. Сообщение самодостаточно: в нём деревья с уровнями, вопрос человеку и готовые строки. Твои действия: задай человеку этот вопрос, перечислив деревья по названиям; сам дерево не выбирай. Ответил «на один раз» — повтори команду с `--tree "<название>"`. Ответил «насовсем» — впиши пару в поле `trees` файла, путь к которому назван в сообщении, и повтори команду. Путь не нужен — `--tree none`. При нескольких проектах в остальных берётся дерево того же состава полей. Нет такого — команда останавливается с тем же вопросом человеку.

## Как читать вывод

- результат — в стандартный вывод, предупреждения и путь HTML-файла — в служебный вывод;
- **картинки и файлы кейса уже на диске.** После `case` и `list` ссылка на вложение в Markdown ведёт на файл
  в хранилище профиля, адрес TestOps стоит в ней заголовком: `![](<путь> "<адрес>")` — открой файл по пути
  своим средством чтения файлов и смотри. Ничего скачивать, распаковывать и разбирать не надо; адрес вида
  `/api/testcase/attachment/<id>/content` требует токена, по нему не ходи. Вложение, которое не скачалось,
  названо в служебном выводе, и ссылка на него ведёт на адрес TestOps.
  Нужны файлы в своём каталоге — `tt-testops attachments <id> --out <каталог>`;
- `Кейс <id> не найден.` и код 1 — кейса нет или нет доступа; ошибка доступа называет код ответа и адрес;
- пометки «Старый формат» и «Пустой сценарий» значат «переписать перед автоматизацией»: в Markdown — строка над сценарием и сводка проблемных кейсов в начале выгрузки `list`; с `--no-marks` пометок нет;
- у автоматизированного кейса без своих шагов сценарий берётся из тестового результата: в Markdown над шагами строка «Нет шагов (сценарий взят из автотеста)», пометка «Пустой сценарий» у такого кейса остаётся;
- `html` — самодостаточная страница с картинками, деревом разделов и двумя видами; без `--out` пишется файлом, путь — в служебный вывод;
- после `list` в служебный вывод идёт строка «Фильтр в TestOps (<проект>): <адрес>» — отдай её человеку, чтобы он открыл ту же выборку в TestOps;
- «Запрос не составить: адрес длиннее, чем принимает сервер TestOps» — набор номеров слишком большой, раздели его на части.

## Чего инструмент не делает

Ничего не пишет в TestOps. Правки вносит человек в интерфейсе; решение переписать кейс — тоже за человеком.

## Первый запуск

```bash
npm install --global @rizias/tt-testops
tt-testops init
tt-testops config init
```

Конфиг готовишь ты: выполни `tt-testops config init`, впиши адрес сервера в `profile.json` (поле
`servers.testops.baseUrl`) и покажи человеку путь к `credentials.json`. Токен человек вписывает сам:
в TestOps открыть профиль → «API-токены» → создать новый → вставить в `credentials.json` как
`{ "testops": { "token": "<токен>" } }`. Токен не спрашивай и в файл не вписывай. Проверка —
`tt-testops config`: токен виден как «задан».

Затем выполни `tt-testops projects`, покажи человеку список проектов сервера и спроси, с какими он работает и как их коротко называть. Впиши ответ в поле `projects` (`{"<номер>": "<имя>"}`), а проект, с которым он работает чаще всего, — в `defaultProject`.

Настройки — профиль `~/.tt-testops/profiles/<профиль>/profile.json`, секреты рядом в `credentials.json`,
текущий профиль в `~/.tt-testops/config.json`. Поля профиля:

| Поле | Что означает | Где взять значение |
|---|---|---|
| `servers.testops.baseUrl` | адрес сервера TestOps | адресная строка браузера |
| `testops.token` (в `credentials.json`) | API-токен | TestOps: профиль → «API-токены» → создать новый |
| `defaultProject` | проект по умолчанию, когда нет `--project` | номер проекта в адресе его страницы |
| `projects` | номер → имя, чтобы писать `--project WEB` | `tt-testops projects` |
| `trees` | рабочее дерево разделов проекта; `"none"` — путь не нужен | `tt-testops trees` |
| `people` | учётка сервера → как показывать | по желанию человека |

Остальные поля — в `references/settings.md`. Проверить, что подхватилось: `tt-testops config`; секрет показан только
признаком «задан» или «не задан». `init` спрашивает, куда ставить скилл: в проект (`.claude/skills`,
`.agents/skills`) или в указанный путь. Без подтверждения ничего не пишется. В домашнюю папку скилл не
ставится: глобальной установки у инструмента нет, назови каталог проекта.

## Обновление

Если tt-testops при запуске сообщил о новой версии — выполни `tt-testops update` и продолжай. Копии
скилла обновятся сами при следующем запуске. До первой публикации `update` завершается кодом 1 с ошибкой
E404 — это норма.

## Справка

- `references/settings.md` — настройки, профили, переменные окружения; читать, когда настраиваешь доступ или команда упала с ошибкой доступа
- `references/commands.md` — все команды и флаги; читать, когда нужной команды нет в этом файле
- `references/aql.md` — язык запросов; читать, когда составляешь запрос или TestOps его отверг
- `references/format.md` — оформление вывода; читать, когда нужен свой формат
