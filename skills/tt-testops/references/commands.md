# Команды подробно

## `case <id>` — один кейс

```bash
tt-testops case <ид-кейса>
tt-testops case <ид-кейса> --format html
```

Вложения кейса — картинки и файлы в тексте, вложения шагов, картинки комментариев — после `case` и `list`
лежат файлами в хранилище профиля: `attachments/case-<ид кейса>/<ид вложения>.<расширение по типу содержимого>`.
Каталог кейса пересобирается при каждой выгрузке: файлы, на которые кейс больше не ссылается, удаляются;
уже лежащий файл заново не скачивается. Ссылка в Markdown ведёт на файл, адрес TestOps стоит в ней
заголовком: `![](<путь> "<адрес>")`, `[<имя>](<путь> "<адрес>")`. Вложение, которое не скачалось, названо в
служебном выводе строкой «кейс N: вложение M не скачалось — причина», ссылка на него остаётся адресом
TestOps.

`attachments <id>` печатает пути файлов вложений кейса; с `--out <каталог>` копирует их туда и печатает новые
пути.

```bash
tt-testops attachments <ид-кейса> --out <каталог>
```

## `list <запрос>` — пачка кейсов по запросу

Рендерит каждый кейс, сверху — сводка с проблемными. Кейсы идут как в TestOps: по названию от А до Я, а если в
ссылке задана сортировка (`sortBy`, `sortDirection`) — по ней. После выгрузки в служебный вывод печатается
строка «Фильтр в TestOps (<проект>): <адрес>» на каждый проект — открыть ту же выборку в TestOps. Если
сам запрос длиннее, чем принимает сервер, выгрузка останавливается сообщением «Запрос не составить…».
Если выгрузка шла по номерам кейсов и не проходит по длине только ссылка, выгрузка идёт, а вместо ссылки
пишется «ссылку не составить». Запрос — AQL или ссылка на фильтр TestOps целиком, в
одинарных кавычках.

```bash
tt-testops list 'tag = "<тег>"' --project <имя> --limit 20
tt-testops list 'https://<хост>/project/<ид>/test-cases?search=W3si...'
tt-testops list --project <ид> --text "<фраза>"
```

**Ссылка на фильтр** принимается с любыми условиями интерфейса TestOps — тегами, кастомными полями, названием,
содержимым, AQL — и с сохранённым фильтром `filterId=<число>`. Условия уходят серверу как есть, выборка та
же, что TestOps показывает по ссылке. Проект берётся из ссылки, `--project` его перекрывает. Дерево `treeId`
задаёт только путь кейсов. Ссылка без единого условия и без `filterId` — ошибка, нечисловой `filterId` — тоже.

**`--text <фраза>`** добавляет условие «Содержимое» из поиска TestOps: кейс попадает в выборку, только когда
выполнены и запрос, и фраза. Без запроса фраза ищется по всему проекту. Фраза применяется к каждой паре
«проект + запрос». Запрос из одних идентификаторов вместе с фразой, условиями ссылки или `filterId` идёт
поиском в проекте, а не выборкой по номерам напрямую. Пустая фраза — ошибка. `--text` есть у `list`,
`count` и `link`.

**Несколько проектов в одном документе.** `--project`, `--rql` и `--rql-file` повторяются; запрос относится
к ближайшему `--project` слева.

```bash
tt-testops list --project <ид-2> --rql 'cf["<Поле-2>"] = "Раздел Б"' \
                --project <ид> --rql 'cf["<Поле-1>"] = "Раздел А"' --format html
```

| Что передали | Что происходит |
|---|---|
| поровну | пара к паре, по порядку |
| один запрос, проектов несколько | запрос выполняется в каждом |
| количества не сходятся | отказ с обоими числами, ничего не выгружается |

- `--limit` считается по каждому проекту отдельно;
- в HTML верхний уровень дерева — проект; Markdown не меняется ни на байт;
- порядок детерминирован: повторный вызов при неизменных кейсах даёт побайтово тот же файл;
- проект без находок назван в служебном выводе, документ собирается из остальных;
- `link` на несколько пар откажется.

**Запрос только по идентификаторам не привязан к проекту** — кейсы берутся из своих проектов, `--project`
не применяется, ненайденные названы в служебном выводе. Любое добавочное условие возвращает запрос в границы
проекта.

```bash
tt-testops list 'id in [<ид-1>, <ид-2>]'
```

## Пометки о состоянии кейса

| Пометка | Что значит |
|---|---|
| Старый формат (Raw Markdown) | сценарий лежит вложением-markdown, а не шагами |
| Пустой сценарий | своих шагов нет вообще; у автотеста при этом показаны шаги тестового результата |

Обе означают одно: перед автоматизацией кейс надо переписать. В Markdown пометка стоит строкой над сценарием,
а выгрузка `list` начинается сводкой проблемных кейсов; в HTML — пометкой у кейса.

`--no-marks` убирает баннер, пометки и сводку; данные кейса не меняются.

## `count <запрос>` — сколько кейсов, без выгрузки

Одно число. Кейсы не скачиваются, `--limit` на него не влияет.

```bash
tt-testops count 'layer = "E2E"' --project <ид>
tt-testops count 'automation = false' --project <ид-1> --project <ид-2>   # число на каждый проект
tt-testops count '<ссылка на фильтр>' --text "<фраза>"
```

## `fields [имя поля]` — что есть в проекте

- без аргумента — обзор: поля с числом значений и слои с числом кейсов; сами значения не печатаются, их тысячи;
- с именем поля — его значения и число кейсов; слой запрашивается по имени `layer`;
- `--find <текст>` — где в проекте встречается слово, готовыми условиями запроса.

```bash
tt-testops fields --project <ид>
tt-testops fields <Поле> --project <ид>
tt-testops fields --find раздел --project <ид>
```

`--find` ищет вхождение подстроки без учёта регистра; не нашлось — вторая попытка со сверкой написания.

## `attachments` и `attachments clear` — хранилище профиля

Данные кейса запрашиваются у сервера при каждой выгрузке заново. В каталоге текущего профиля
`~/.tt-testops/profiles/<профиль>/` лежат только файлы
вложений в каталогах кейсов `attachments/case-<ид>/`, сессии доступа в `sessions/` и списки деревьев проекта
в `trees/`. Уже лежащий файл вложения не перекачивается: в TestOps вложения
неизменяемы.

JWT-сессия хранится локально, отдельно для каждой пары «адрес сервера и учётные данные», и
переиспользуется между запусками, пока не истёк её срок; сессия без срока — пока сервер её не отверг. API-токен для такой
привязки не сохраняется. `attachments clear` удаляет каталоги `attachments/`, `sessions/` и `trees/` целиком; не удалось удалить
часть — в служебном выводе названо, что осталось, и очистка не объявлена.

```bash
tt-testops attachments          # число файлов вложений, их объём и срок сессии
tt-testops attachments clear
```

## `projects` — согласованный список

Печатает словарь `projects` из `profile.json`, отмечает наличие каждого на сервере и отдельно называет
проекты сервера, которых нет в конфигурации. С проектом вне списка работать можно — будет предупреждение.

## `trees` — из чего складывается путь кейса

Путь — это уровни дерева разделов. Деревьев у проекта бывает несколько, собраны из разных полей.

```bash
tt-testops trees --project <ид>
```

- одно дерево — берётся молча; ни одного — путь пустой;
- несколько, а рабочее не выбрано — `case` и `list` останавливаются с кодом 1: `list` — до скачивания первого
  кейса, файл из `--out` не создаётся. Сообщение самодостаточно: называет проект, перечисляет деревья по
  названиям — тем же, что в интерфейсе TestOps, — с их уровнями, говорит, что спросить у человека, и даёт
  готовые строки: `--tree "<название>"` на один вызов; `"trees": { "<ид>": "<название>" }` с полным путём к
  `profile.json` — насовсем; `--tree none` либо `"none"` в том же поле — путь не нужен. Выгрузка без дерева —
  плоский список без разделов, поэтому молча она не делается;
- дерево выбирается **названием**, без учёта регистра; идентификатор принимается наравне. Названного дерева у
  проекта нет — переименовали, удалили, опечатка — та же остановка с перечнем деревьев;
- командам без пути в выводе — `attachments`, `count`, `link`, `fields`, `projects` — дерево не нужно.

При нескольких проектах `--tree` один на вызов: в остальных берётся дерево **того же состава полей**. Нет
такого — команда останавливается с тем же вопросом человеку.

## `link <запрос>` и `setup [путь]`

`link` печатает ссылку на фильтр TestOps — открыть в браузере или переслать коллеге. В ссылку попадают все
условия: запрос, условия переданной ссылки, фраза `--text` и `filterId`. `setup` объясняет, как
подключить инструмент к конкретному проекту, и ничего не меняет.

```bash
tt-testops link 'cf["<Поле>"] = "Раздел А"' --project <ид>
tt-testops link 'tag = "<тег>"' --project <ид> --text "<фраза>"
```

## Устойчивость запросов

Каждое обращение к TestOps выполняется один раз, без повторов и пауз. Первый `401` запускает однократное
восстановление сессии. Исключение — скачивание вложения: при обрыве связи или ответе 5xx оно повторяется до
3 раз подряд; ответ 404 не повторяется.

Язык запросов — [aql.md](aql.md). Свой формат вывода — [format.md](format.md). Настройки подробно —
[settings.md](settings.md).
