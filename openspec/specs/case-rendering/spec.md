# case-rendering Specification

## Purpose
Как нормализованный кейс превращается в то, что читает человек или разбирает другая программа: байтово стабильный Markdown, структурный JSON и профиль формата, позволяющий менять оформление без правки кода.

## Requirements

### Requirement: Стабильность Markdown

Один и тот же нормализованный кейс SHALL всегда давать байтово одинаковый Markdown. Стабильность MUST быть закреплена эталонными снимками вывода — по одному на каждый вариант: одиночный кейс и пачка.

#### Scenario: Повторный рендер того же кейса

- **WHEN** один и тот же нормализованный кейс отрендерен дважды
- **THEN** обе выдачи совпадают побайтово

### Requirement: Контракт Markdown

Markdown SHALL соблюдать следующие константы формата:

- шапка одиночного отчёта — `# **{имя}** (ID: {идентификатор})`, звёздочки обязательны;
- заголовки разделов — ровно `### Описание`, `### Предварительное условие`, `### Сценарий`, `### Ожидаемый результат`;
- пустой сценарий выводится подстрокой `Нет шагов`;
- вложенность шага — 2 пробела на уровень;
- кейсы в пачке идут подряд, каждый начинается с шапки `# **{имя}** (ID: {идентификатор})`; между кейсами одна пустая строка, служебных строк-разделителей нет;
- одиночный отчёт MUST NOT содержать сводку `📊 Сводка`;
- версия формата MUST NOT попадать в поток Markdown.

Вывод SHALL быть корректным UTF-8 с кириллицей: без `?`, без `�`, без буквальных последовательностей `\n` и `\r`.

#### Scenario: Отчёт по одному кейсу

- **WHEN** отрендерен один кейс
- **THEN** вывод начинается с шапки указанного вида и не содержит сводки

#### Scenario: Отчёт по пачке кейсов

- **WHEN** отрендерена пачка из трёх кейсов
- **THEN** каждый кейс начинается с шапки, между кейсами нет служебных строк, а сверху идёт сводка

#### Scenario: Шаг третьего уровня вложенности

- **WHEN** шаг вложен на два уровня ниже верхнего — третья по счёту ступень
- **THEN** его строка начинается с 4 пробелов: верхний уровень идёт без отступа, каждая следующая ступень добавляет 2 пробела

### Requirement: Верность исходной разметке

Описание и предусловие SHALL рендериться со своей исходной разметкой: нумерованные и
маркированные списки, выделение, ссылки. Продукт MUST NOT вырезать разметку ради простоты вывода.

#### Scenario: Длинное описание со списком и ссылками

- **WHEN** описание кейса содержит нумерованный список и ссылки
- **THEN** в выводе сохраняются и нумерация, и ссылки

### Requirement: Версия контракта вне потока

Идентификатор и версия контракта формата SHALL быть доступны отдельно от вывода — например,
командой или полем структурного вывода. Ни то, ни другое MUST NOT попадать в поток Markdown
по умолчанию.

#### Scenario: Потребителю нужна версия контракта

- **WHEN** потребителю требуется узнать версию контракта формата
- **THEN** он получает её вне потока Markdown, а сам Markdown остаётся без служебных строк

### Requirement: Структурный вывод

Продукт SHALL уметь выдавать кейс структурой в формате JSON. Markdown и JSON SHALL строиться из одного и того же нормализованного кейса чистыми преобразованиями, без обращений к сети.

Структура кейса SHALL содержать проект, из которого кейс взят: числовой идентификатор и имя, когда оно известно из словаря `projects` файла `profile.json`. Markdown при этом SHALL остаться без изменений — его формат заморожен, и проект в нём не подписывается.

#### Scenario: Один кейс в JSON

- **WHEN** запрошен формат `json`
- **THEN** продукт выводит структуру со всем составом тест-кейса; служебные каналы рендеринга — например размеченный текст шага для HTML — в неё не попадают: они дублируют уже выведенные строки сценария

#### Scenario: Проект виден в структуре

- **WHEN** запрошен формат `json` по выборке из двух проектов
- **THEN** у каждого кейса виден проект, из которого он взят

### Requirement: Профиль формата

Оформление Markdown SHALL задаваться проверяемым профилем формата в виде JSON, а не быть зашитым в код. Без объявления новой версии контракта профилем SHALL меняться: подписи полей шапки, порядок разделов, тексты предупреждений о сценарии, оформление шага и общего шага, состав и порядок кастомных полей, обезличивание адресов. Профиль по умолчанию SHALL воспроизводить исторический формат байт в байт.

Критичные для разбора поля — шапка `# **{имя}** (ID: {идентификатор})`, заголовки разделов и отступ шага — при действующей версии контракта заморожены: их разбирают сторонние инструменты, и профиль, меняющий их, SHALL отвергаться до обращения к TestOps. Менять их SHALL быть можно только профилем, объявившим новую версию контракта; такой вывод не передаётся потребителям прежней версии без согласования.

Строки, которые продукт печатает над сценарием — баннеры старого и несогласованного формата, — это оформление Markdown, и они SHALL задаваться профилем. Сообщения отчёта команды `audit` оформлением не являются и SHALL задаваться правилами пометок.

Профиль решает, как кейс показан. Настройки времени выполнения — поля AQL, карта проектов, таймауты — MUST жить в конфигурации, а не в профиле. Адреса эндпоинтов API MUST быть константами в коде и MUST NOT быть настройкой пользователя.

#### Scenario: Пользователь переименовал раздел под новой версией контракта

- **WHEN** профиль объявляет новую версию контракта и заменяет заголовок `### Описание` на `### Что проверяем`
- **THEN** вывод использует новый заголовок без пересборки продукта

#### Scenario: Профиль ломает разбор

- **WHEN** профиль объявлен совместимым с историческим форматом, но меняет поле, критичное для разбора
- **THEN** продукт отказывается стартовать и называет несовпавшее поле

### Requirement: Связи кейса в структурном выводе

Структурный вывод SHALL содержать задачи баг-трекера, людей с ролями, ссылки и связанные кейсы. У задачи SHALL быть её ключ и адрес, чтобы по ним можно было обратиться в баг-трекер отдельным инструментом.

Markdown MUST оставаться без изменений: его формат заморожен.

#### Scenario: Задача баг-трекера в JSON

- **WHEN** у кейса есть задача баг-трекера и запрошен формат `json`
- **THEN** в выводе видны её ключ, заголовок, состояние и адрес

#### Scenario: Markdown не изменился

- **WHEN** тот же кейс отрендерен в Markdown
- **THEN** вывод побайтово совпадает с выводом до этой работы

### Requirement: Ссылки кейса в Markdown

Строка `- **Ссылки:**` в шапке кейса SHALL выводить каждую ссылку кейса ссылкой Markdown — `[подпись](адрес)`; ссылки разделяются запятой и пробелом, порядок — как у сервера, повторы одной и той же пары «подпись и адрес» выводятся один раз.

Ссылка без подписи SHALL выводиться своим адресом. Ссылка без адреса SHALL выводиться своей подписью. Подпись, равная адресу, SHALL выводиться одним адресом, без дублирования.

При включённом в профиле формата обезличивании ссылок адрес SHALL сводиться к домену — так же, как в тексте кейса.

Кейс без ссылок строки `- **Ссылки:**` не содержит.

#### Scenario: Ссылка с подписью и адресом

- **WHEN** у кейса есть ссылка с подписью `<подпись>` и адресом `https://tracker.example/<путь>`
- **THEN** строка ссылок содержит `[<подпись>](https://tracker.example/<путь>)`

#### Scenario: Ссылка без подписи

- **WHEN** у ссылки кейса есть только адрес
- **THEN** в строке ссылок выведен этот адрес целиком

#### Scenario: Обезличивание включено

- **WHEN** профиль формата включает обезличивание ссылок
- **THEN** адрес в строке ссылок сведён к домену
