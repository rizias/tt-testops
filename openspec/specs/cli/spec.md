# cli Specification

## Purpose
Командная строка — единственная поверхность продукта. Всё, что умеет движок, доступно через неё; знание о том, как её звать, живёт в скилле для агентов.

## Requirements

### Requirement: Единственная поверхность

Продукт SHALL предоставлять одну поверхность для вызова извне — командную строку `tt-testops`. Постоянно запущенного процесса, службы или второго исполняемого файла у продукта MUST NOT быть.

Тот же пакет SHALL экспортировать библиотеку для проектов, которые пишут на TypeScript и предпочитают вызвать шлюз напрямую. Это второй способ вызова того же кода, а не вторая поверхность: разговаривает с TestOps по-прежнему только он.

#### Scenario: Агенту нужен доступ к кейсам

- **WHEN** агенту требуется получить тест-кейсы
- **THEN** он вызывает команду `tt-testops`, а не отдельный постоянно запущенный процесс

### Requirement: Состав команд

Командная строка SHALL предоставлять команды:

- `case <id>` — один кейс по идентификатору;
- `list <AQL>` — все кейсы по запросу, каждый отрендерен, сверху сводка;
- `audit <AQL>` — только пометки по запросу, без содержимого кейсов;
- `count <AQL>` — число подходящих кейсов без их выгрузки.

Командная строка SHALL предоставлять команду `fields`. Без аргумента она SHALL печатать справочник проекта: кастомные поля с числом значений у каждого и слои проекта с числом кейсов. С названием поля аргументом она SHALL печатать значения этого поля и число кейсов на каждом; название слоя принимается наравне с именем кастомного поля. С флагом `--find <текст>` она SHALL печатать поля, значения и слои, которым этот текст соответствует, в виде условий запроса.

Командная строка SHALL предоставлять команду `link`, печатающую ссылку на фильтр TestOps по переданному запросу и проекту.

Командная строка SHALL предоставлять команду `projects`, печатающую согласованный список проектов и, отдельной группой, проекты сервера, не внесённые в конфигурацию.

Командная строка SHALL предоставлять локальные команды, которым сервер не нужен: `cache` — состояние и очистка локального хранилища (поведение задано способностью `local-cache`), `setup` — печатает, как подключить продукт к названному проекту, ничего не меняя, `config` — просмотр настроек и управление профилями (требование выше), `init` — раскладка скилла (требование ниже) и `update` — обновление пакета до последней версии (поведение задано способностью `distribution`).

Командная строка SHALL отвечать на `--version` версией установленного пакета.

Аргумент, принимающий AQL, у команд `list`, `audit`, `count` и `link` SHALL принимать также ссылку на фильтр TestOps. То же SHALL работать через `--rql` и `--rql-file`.

Запрошенный кейс SHALL отдаваться целиком: вместе с текстом продукт SHALL класть на диск все вложения этого кейса — картинки и файлы шагов, описания, ожидаемого результата и комментариев — и называть путь каждого в потоке ошибок. Ни выгрузка в HTML ради встроенных данных, ни разбор вывода сторонними средствами для этого MUST NOT требоваться.

Файлы SHALL лежать в хранилище действующего профиля, а имя файла SHALL нести номер вложения и расширение по типу содержимого, чтобы файл открывался обычной программой. Markdown при этом MUST NOT меняться: ссылки в нём остаются адресами TestOps.

Командная строка SHALL предоставлять команду `attachments <id кейса>`, которая кладёт те же файлы в каталог, заданный флагом `--out`, и печатает их пути в стандартный вывод.

Вложение, которое не скачалось, SHALL быть названо в потоке ошибок; остальные при этом сохраняются.

#### Scenario: Запрос одного кейса

- **WHEN** выполнено `tt-testops case <ид-кейса>`
- **THEN** в стандартный вывод попадает отчёт по кейсу <ид-кейса>

#### Scenario: Поля проекта

- **WHEN** выполнено `tt-testops fields --project <ид>`
- **THEN** в стандартный вывод попадают кастомные поля проекта <ид> с числом значений и слои проекта с числом кейсов

#### Scenario: Значения поля

- **WHEN** выполнено `tt-testops fields <Поле> --project <ид>`
- **THEN** в стандартный вывод попадают значения поля с числом кейсов, по убыванию

#### Scenario: Значения слоя

- **WHEN** выполнено `tt-testops fields layer --project <ид>`
- **THEN** в стандартный вывод попадают слои, используемые в проекте <ид>, с числом кейсов

#### Scenario: Поиск, где встречается значение

- **WHEN** выполнено `tt-testops fields --find раздел --project <ид>`
- **THEN** в стандартный вывод попадают условия запроса, которым это соответствует

#### Scenario: Число кейсов по запросу

- **WHEN** выполнено `tt-testops count 'layer = "E2E"' --project <ид>`
- **THEN** в стандартный вывод попадает число и ничего больше

#### Scenario: Ссылка по запросу

- **WHEN** выполнено `tt-testops link 'tag = "<тег>"' --project <ид>`
- **THEN** в стандартный вывод попадает один адрес, который открывается в браузере и показывает эту выборку

#### Scenario: Список проектов

- **WHEN** выполнено `tt-testops projects`
- **THEN** в стандартный вывод попадают проекты из конфигурации с признаком наличия на сервере и, отдельно, проекты сервера вне конфигурации

#### Scenario: Список в структурном виде

- **WHEN** выполнено `tt-testops projects --format json`
- **THEN** вывод содержит обе группы структурой

#### Scenario: Запрос версии

- **WHEN** выполнено `tt-testops --version`
- **THEN** в стандартный вывод попадает версия и ничего больше

#### Scenario: Выгрузка по ссылке из задачи

- **WHEN** выполнено `tt-testops list '<ссылка на фильтр>'`
- **THEN** продукт выгружает кейсы этой выборки в проекте, указанном в ссылке

#### Scenario: Проект задан явно поверх ссылки

- **WHEN** передана ссылка на фильтр проекта <ид> и одновременно `--project <ид-2>`
- **THEN** запрос выполняется в проекте <ид-2>

#### Scenario: У кейса есть картинка

- **WHEN** выполнено `tt-testops case <id>`, а в кейсе есть вложение-картинка
- **THEN** файл картинки лежит на диске, его путь назван в потоке ошибок, и открыть его можно обычной программой

#### Scenario: Вложения в указанный каталог

- **WHEN** выполнено `tt-testops attachments <id> --out <каталог>`
- **THEN** файлы вложений кейса лежат в этом каталоге, а их пути напечатаны в стандартный вывод

### Requirement: Флаги команд

Каждая команда SHALL поддерживать:

- `--format markdown|json`, по умолчанию `markdown`;
- `--out <файл>` — запись результата в файл вместо экрана;
- `--project <id|имя>` — выбор проекта;
- `--limit <N>` — предел количества кейсов для команд, работающих с выборкой.

Каждая команда SHALL дополнительно поддерживать общие флаги настроек: `--profile <профиль>` — выбор профиля контура, и `--config <путь>` — путь к файлу `profile.json`, используемому вместо выбора по профилю; каталогом профиля в этом случае считается каталог указанного файла. Поведение этих флагов и порядок, в котором они участвуют в выборе профиля, заданы требованием «Источник доступа» способности `testops-access`.

Сверх этого `case` и `list` SHALL принимать `--format html`, а `case` — ещё и `--format raw`: сырой ответ TestOps как есть, без нормализации. `raw` нужен, когда надо посмотреть, что именно прислал сервер, и MUST NOT поддерживаться другими командами.

Флаг `--find <текст>` SHALL поддерживаться командой `fields` и MUST NOT поддерживаться другими командами.

Предел `--limit` MUST NOT влиять на число, которое печатает `count`.

Запрос AQL SHALL приниматься позиционным аргументом, либо флагом `--rql`, либо из файла флагом `--rql-file`.

Флаги `--project`, `--rql`, `--rql-file`, `--limit`, `--out`, `--format`, `--for`, `--find`, `--profile` и `--config` SHALL требовать отдельное значение. Отсутствующее значение и следующий токен, начинающийся с `--`, MUST приводить к ошибке разбора, а не становиться значением флага.

Значение `--limit` SHALL быть целым числом больше нуля. При ином значении продукт SHALL завершиться ошибкой разбора и SHALL NOT обращаться к TestOps за выгрузкой.

#### Scenario: Запрос из файла

- **WHEN** выполнено `tt-testops list --rql-file q.txt --project <ид-2>`
- **THEN** содержимое `q.txt` используется как запрос AQL

#### Scenario: Формат по умолчанию

- **WHEN** флаг `--format` не задан
- **THEN** вывод идёт в Markdown

#### Scenario: Флаг без значения

- **WHEN** выполнено `tt-testops list --rql --project <ид>`
- **THEN** продукт сообщает, что флагу `--rql` нужно значение, и не принимает `--project` за запрос

#### Scenario: Недопустимый предел

- **WHEN** `--limit` получил `abc`, отрицательное число или ноль
- **THEN** продукт сообщает, что предел должен быть целым числом больше нуля, и ничего не выгружает

#### Scenario: Поиск значения не там

- **WHEN** выполнено `tt-testops list --find раздел`
- **THEN** продукт сообщает, что `--find` есть только у `fields`

### Requirement: Разделение потоков

Продукт SHALL писать в стандартный вывод ровно один поток — результат. Диагностика, предупреждения и прогресс MUST идти в поток ошибок.

#### Scenario: Перенаправление результата в файл

- **WHEN** вывод команды перенаправлен в файл, а по ходу работы возникло предупреждение
- **THEN** файл содержит только результат, предупреждение видно в терминале

### Requirement: Понятная ошибка запроса

Ошибка выполнения SHALL называть причину человеческим языком. Голый код ответа с адресом запроса MUST NOT быть единственным, что видит пользователь.

#### Scenario: Неверный синтаксис AQL

- **WHEN** передан запрос с голым именем кастомного поля, например `<Поле> = "Раздел А"`, и сервер отвечает `invalid.aql`
- **THEN** продукт сообщает, что кастомные поля адресуются как `cf["<Поле-1>"]`, и показывает исправленный вариант запроса

### Requirement: Формат html

Флаг формата SHALL принимать значение `html` наряду с `markdown` и `json`, для команд `case` и `list`.

Поскольку HTML предназначен для открытия в браузере, а не для чтения в терминале, при `--format html` без `--out` продукт SHALL записать файл сам. Явный `--out` имеет приоритет.

**Куда пишется файл.** Когда путь не указан, файл SHALL создаваться в том каталоге, откуда вызвана команда. Когда в `--out` указано имя без каталога, файл SHALL создаваться там же.

**Как называется файл.** Имя по умолчанию SHALL содержать отметку времени вида `ГГГГ-ММ-ДД-ЧЧММСС`, чтобы прошлая выгрузка не затиралась новой: `cases-2026-08-30-024512.html` для команды `list` и `case-<ид-кейса>-2026-08-30-024512.html` для команды `case`. Отметка времени берётся по часам машины, откуда вызвана команда.

**Что печатается по окончании.** Продукт SHALL напечатать в поток ошибок одной строкой: полный путь к файлу, его размер и время, которое заняла работа. Размер SHALL называться числом с единицей, время — числом в секундах с одним знаком после запятой. Строка SHALL печататься и тогда, когда путь задан через `--out`.

#### Scenario: Один кейс в HTML

- **WHEN** выполнено `tt-testops case <ид-кейса> --format html --out case.html`
- **THEN** создан файл `case.html`, открывающийся в браузере с картинками кейса, и напечатана строка с полным путём, размером и временем работы

#### Scenario: Пачка в HTML без указания файла

- **WHEN** выполнено `tt-testops list '<запрос>' --format html`
- **THEN** продукт создаёт в текущем каталоге файл с именем `cases-<отметка времени>.html` и печатает в поток ошибок его полный путь, размер и время работы, не вываливая HTML в терминал

#### Scenario: Прошлая выгрузка не затирается

- **WHEN** та же команда выполнена дважды
- **THEN** созданы два файла с разными именами, и ни один не перезаписан

#### Scenario: Формат html у команды без представления

- **WHEN** `--format html` передан команде `fields`, `projects` или `link`
- **THEN** продукт сообщает, что этот формат для команды не поддерживается

### Requirement: Команда установки скилла

Командная строка SHALL предоставлять команду `init`, раскладывающую скилл в проект.

Команда SHALL спросить пользователя, куда ставить скилл, прежде чем создать хотя бы один файл, и SHALL NOT выбирать каталоги за него. Поддерживаемые каталоги — `.claude/skills/` и `.agents/skills/` проекта; глобальных каталогов в вопросе MUST NOT быть.

Вопрос SHALL называть проект, в который пойдёт установка, и SHALL перечислять поддерживаемые каталоги. Перед записью SHALL показываться полный список конечных путей и запрашиваться подтверждение.

Команда SHALL NOT раскладывать скилл во все поддерживаемые каталоги сразу — ни по умолчанию, ни при пустом ответе.

Ответ SHALL задаваться и заранее: путь к проекту аргументом, каталоги флагом `--for` со значениями `claude` и `agents` через запятую. Когда каталоги заданы флагом, вопросы не задаются.

Когда задать вопрос невозможно — стандартный ввод не является терминалом — команда SHALL завершиться с объяснением, как указать каталоги флагом, и SHALL NOT изменить ни одного файла.

Команда SHALL печатать отчёт: какие копии поставлены, какие пропущены и почему, какие мёртвые записи реестра удалены.

#### Scenario: Установка спрашивает, куда ставить

- **WHEN** выполнено `tt-testops init` в терминале
- **THEN** названы проект и поддерживаемые каталоги, и до подтверждения не создано ни одного файла

#### Scenario: Пустой ответ ничего не ставит

- **WHEN** на вопрос о каталогах не выбрано ни одного
- **THEN** команда завершается, не создав ни одного файла

#### Scenario: Явный выбор без вопроса

- **WHEN** выполнено `tt-testops init C:\путь\к\проекту --for claude`
- **THEN** скилл появляется только в `.claude/skills/` этого проекта, вопросы не задаются

#### Scenario: Вопрос задать нельзя

- **WHEN** выполнено `tt-testops init` без `--for` и стандартный ввод не терминал
- **THEN** ни одного файла не создано и объяснено, как указать каталоги флагом

### Requirement: Несколько проектов в одном вызове

Команда `list` SHALL принимать несколько пар «проект + запрос» за один вызов и собирать из них один документ. Флаги `--project`, `--rql` и `--rql-file` SHALL повторяться.

Позиционные запросы SHALL участвовать в связывании наравне с `--rql` и `--rql-file`: каждый относится к ближайшему `--project` слева. Смешение форм MUST NOT считаться ошибкой само по себе.

Ссылку на фильтр продукт SHALL разобрать до связывания пар. Проект из ссылки SHALL считаться проектом этой пары, когда явный `--project` для запроса не задан; явный проект SHALL иметь приоритет.

Запросы связываются с проектами так: когда запросов столько же, сколько проектов, каждый запрос относится к ближайшему `--project` слева от него; когда запрос один, а проектов несколько, он выполняется в каждом из них; в остальных случаях продукт SHALL завершиться ошибкой, назвав, сколько проектов и сколько запросов получил, и SHALL NOT выгрузить ничего.

Ноль запросов при двух и более проектах SHALL считаться несовпадением количеств и приводить к тому же отказу. Один проект без запроса SHALL по-прежнему означать все кейсы этого проекта.

Проект, которому при равных количествах не досталось ни одного запроса, SHALL называться в ошибке поимённо: молча выбросить его из выборки нельзя.

Кейсы в документе SHALL идти в порядке перечисления проектов, а внутри проекта — в том порядке, который отдал поиск. Один и тот же кейс SHALL попадать в документ один раз.

`--limit` SHALL ограничивать каждый проект отдельно.

Команда `audit` SHALL принимать те же пары: разбор флагов у команд общий, и однопроектный аудит выборки, собранной из нескольких проектов, вводил бы в заблуждение.

Команда `link` SHALL отказываться строить ссылку, когда пар передано больше одной: выборку из нескольких проектов TestOps одной ссылкой не показывает.

Проект, не давший ни одного кейса, SHALL называться в потоке ошибок, а документ SHALL собираться из остальных. Когда кейсов не нашлось ни в одном проекте, продукт SHALL сообщить об этом так же, как при однопроектном запросе.

#### Scenario: Разные запросы в разных проектах

- **WHEN** выполнено `tt-testops list --project <ид-2> --rql 'cf["<Поле-2>"] = "Раздел Б"' --project <ид> --rql 'cf["<Поле-1>"] = "Раздел А"'`
- **THEN** один документ содержит кейсы обоих проектов

#### Scenario: Позиционный запрос вместе с флагом

- **WHEN** выполнено `tt-testops list --project <ид-2> --rql 'A' --project <ид> 'B'`
- **THEN** запрос `A` выполняется в проекте <ид-2>, а позиционный запрос `B` — в проекте <ид>

#### Scenario: Две ссылки без явного проекта

- **WHEN** переданы две ссылки на фильтры разных проектов без `--project`
- **THEN** продукт разбирает обе ссылки и собирает документ из двух пар «проект + запрос»

#### Scenario: Один запрос на несколько проектов

- **WHEN** выполнено `tt-testops list 'tag = "<тег>"' --project <ид-1> --project <ид-2>`
- **THEN** запрос выполняется в обоих проектах, результат — один документ

#### Scenario: Количества не сходятся

- **WHEN** передано три проекта и два запроса
- **THEN** продукт завершается ошибкой, называя оба числа, и не выгружает ничего

#### Scenario: Несколько проектов без запросов

- **WHEN** переданы два `--project` и ни одного запроса
- **THEN** продукт завершается ошибкой, называя два проекта и ноль запросов, и не выгружает ничего

#### Scenario: Проекту не досталось запроса

- **WHEN** запросов столько же, сколько проектов, но оба относятся к одному и тому же проекту
- **THEN** продукт называет проект, оставшийся без запроса, и не выгружает ничего

#### Scenario: В одном из проектов пусто

- **WHEN** один проект не дал кейсов, а остальные дали
- **THEN** он назван в потоке ошибок, а документ собран из остальных

#### Scenario: Повтор вызова

- **WHEN** тот же вызов выполнен дважды, а кейсы не менялись
- **THEN** оба раза получается побайтово одинаковый файл

### Requirement: Выборка только по идентификаторам

Когда запрос состоит только из идентификаторов кейсов и не содержит других условий, продукт SHALL находить кейсы по идентификатору напрямую и SHALL NOT ограничивать выборку одним проектом. Кейсы разных проектов SHALL попадать в один документ.

Запросом только по идентификаторам SHALL считаться любое выражение, целиком составленное из условий `id = N` и `id in [N, ...]`, соединённых оператором `or`, с произвольными пробелами и скобками. Любой иной оператор или условие MUST переводить запрос на обычный поиск в проекте.

Проект такому запросу не нужен: идентификатор кейса в TestOps единственный на весь сервер. Когда один или несколько `--project` всё же переданы, продукт SHALL одним сообщением перечислить все проекты, которые не применялись.

Идентификатор, которого нет или к которому нет доступа, SHALL называться в потоке ошибок поимённо, а остальные кейсы SHALL выгружаться.

Запрос, где к идентификаторам добавлено любое другое условие, SHALL выполняться поиском в пределах проекта, как всякий другой.

`--limit` SHALL ограничивать и такой запрос — первыми идентификаторами списка, — и продукт SHALL сказать в потоке ошибок, сколько идентификаторов из скольких взято. Молча игнорировать переданный флаг MUST NOT.

Один и тот же запрос по идентификаторам, повторённый для нескольких проектов, SHALL выполняться один раз: проекты для него роли не играют.

#### Scenario: Идентификаторы из разных проектов

- **WHEN** выполнено `tt-testops list 'id in [<ид-1>, <ид-2>]'`
- **THEN** в выборку попадают оба кейса, хотя лежат они в разных проектах

#### Scenario: Условия по идентификаторам соединены or

- **WHEN** выполнен запрос `(id = 1 or (id in [2, 3]))`
- **THEN** он выполняется как запрос только по идентификаторам 1, 2 и 3

#### Scenario: Проект при запросе по идентификаторам

- **WHEN** такому запросу передан `--project <ид>`
- **THEN** кейсы берутся из своих проектов, а продукт сообщает, что проект не применялся

#### Scenario: Идентификатора нет

- **WHEN** среди идентификаторов есть несуществующий
- **THEN** он назван в потоке ошибок, а остальные кейсы выгружены

#### Scenario: Предел на списке идентификаторов

- **WHEN** выполнено `tt-testops list 'id in [1, 2, 3]' --limit 2`
- **THEN** выгружены первые два кейса, а в потоке ошибок сказано, сколько идентификаторов из скольких взято

#### Scenario: Один запрос по идентификаторам на несколько проектов

- **WHEN** запрос только по идентификаторам передан вместе с двумя `--project`
- **THEN** кейсы выгружены один раз, а не дважды

#### Scenario: Идентификаторы вместе с другим условием

- **WHEN** выполнено `tt-testops list 'id in [<ид-1>, <ид-2>] and automation = false' --project <ид>`
- **THEN** запрос выполняется поиском в проекте <ид>, как обычный запрос

### Requirement: Рабочее дерево проекта

Рабочее дерево SHALL определяться в таком порядке, первым сработавшим источником:

1. значение флага `--tree` этого вызова — название дерева, его идентификатор либо `none`, «пути не надо»;
2. дерево, указанное в переданной ссылке на фильтр TestOps;
3. настройка проекта в поле `trees` файла `profile.json`;
4. единственное дерево проекта.

**Дерево называется так, как его видит человек.** В интерфейсе TestOps у дерева есть название, а идентификатора человек не видит, поэтому и флаг `--tree`, и поле `trees` SHALL принимать название дерева; идентификатор SHALL приниматься наравне с ним. Название сравнивается целиком, без учёта регистра и крайних пробелов. Поле `trees` — соответствие «проект → название или идентификатор дерева», вместо них допускается `none` — «пути не надо». Значение иного вида SHALL приводить к ошибке настроек, а не отбрасываться молча. Список полей дерева в настройках MUST NOT храниться: состав знает сервер.

Когда названного дерева у проекта нет — его переименовали, удалили или в названии опечатка, — команды `case` и `list` SHALL остановиться тем же сообщением, что и при отсутствии выбора, назвав искомое значение; путь молча пустым MUST NOT оставаться.

Флаг `--tree` относится ко всему вызову, а идентификатор дерева живёт внутри одного проекта. Когда в вызове несколько проектов, в остальных проектах SHALL браться дерево того же состава: имена деревьев в разных проектах различаются, а набор полей — `<Поле-1> / <Поле-2> / …` — совпадает, и именно он делает дерево тем же самым. Совпадением считается равенство упорядоченного списка имён полей. Когда такого дерева в проекте нет, другое дерево вместо него MUST NOT браться: путь по дереву иного состава в общем документе неверен. Команды `case` и `list` в этом случае SHALL остановиться тем же сообщением, назвав искомое дерево и деревья этого проекта; продолжить можно, убрав флаг и записав рабочее дерево каждого проекта в поле `trees`.

Когда у проекта несколько деревьев и ни один источник не сработал, команды `case` и `list` SHALL остановиться с ошибкой и кодом возврата 1 и MUST NOT отдавать результат с пустым путём: выгрузка без дерева — плоский список, которым нельзя пользоваться, а узнать об этом после выгрузки поздно. У команды `list` проверка SHALL выполняться по всем проектам вызова до скачивания первого кейса; у команды `case` проект становится известен из самого кейса, и проверка выполняется сразу после его получения, до вывода. **Сообщение самодостаточно.** По нему одному и агент, и человек SHALL понять, что произошло и что делать дальше, не открывая документацию. Сообщение SHALL содержать: проект — номер и, когда оно известно, имя; причину остановки; все деревья проекта — название, как в интерфейсе TestOps, число уровней и имена уровней по порядку; что спросить у человека — какое из перечисленных деревьев рабочее для этого проекта; и три способа продолжить с готовым к вставке текстом: флаг `--tree "<название>"` на этот вызов; строку для поля `trees` с полным путём к действующему файлу `profile.json`; значение `none` — флагом или в поле, — когда путь не нужен. Готовый текст SHALL использовать названия деревьев, а не идентификаторы. Файл, названный флагом `--out`, при этом MUST NOT создаваться.

Команды, в выводе которых пути нет, — `audit`, `attachments`, `count`, `link`, `fields`, `projects` — выбора дерева MUST NOT требовать. При значении `none` ни ошибки, ни предупреждения нет.

Команда `trees` SHALL показывать деревья проекта: название, идентификатор, поля по порядку и пометку у рабочего, а также готовую строку выбора каждого дерева по названию.

#### Scenario: Деревьев несколько, выбора нет

- **WHEN** у проекта два дерева, ни флага, ни ссылки, ни настройки нет, и выполнена команда `list`
- **THEN** команда завершается кодом 1 до скачивания кейсов, сообщение называет оба дерева и три способа продолжить, файл из `--out` не создан

#### Scenario: Путь не нужен на один вызов

- **WHEN** тот же вызов сделан с `--tree none`
- **THEN** кейсы выгружены с пустым путём, без ошибки и без предупреждения

#### Scenario: Команде без пути дерево не нужно

- **WHEN** у проекта два дерева, выбора нет, и выполнена команда `audit`
- **THEN** отчёт выдан, выбора дерева команда не требует

#### Scenario: Владелец отказался от пути

- **WHEN** для проекта в поле `trees` указано `none`
- **THEN** путь пуст и предупреждение не печатается

#### Scenario: Дерево задано флагом

- **WHEN** тот же вызов сделан с `--tree` и идентификатором одного из деревьев
- **THEN** путь собран по этому дереву, поле `trees` при этом не меняется

#### Scenario: Показ деревьев

- **WHEN** выполнено `tt-testops trees --project <проект>`
- **THEN** показаны все деревья проекта с их полями по порядку и отмечено рабочее

#### Scenario: Дерево выбрано названием

- **WHEN** вызов сделан с `--tree "<название>"`, либо в поле `trees` для проекта записано это название в другом регистре
- **THEN** путь собран по дереву с этим названием

#### Scenario: Названного дерева нет

- **WHEN** в поле `trees` для проекта записано название, которого среди деревьев проекта нет
- **THEN** `list` останавливается до скачивания кейсов, сообщение называет искомое значение и перечисляет деревья проекта

#### Scenario: По сообщению понятно, что делать

- **WHEN** `list` остановилась из-за невыбранного дерева
- **THEN** сообщение содержит названия всех деревьев с их уровнями, вопрос, который нужно задать человеку, полный путь к `profile.json` и готовые строки для флага и для поля с названием дерева

### Requirement: Команда config

Командная строка SHALL предоставлять команду `config` для просмотра настроек и управления профилями. Команда MUST NOT обращаться к серверу TestOps.

Без подкоманды `config` SHALL печатать: путь общего файла `~/.tt-testops/config.json`, выбранный профиль и способ, которым он выбран (`flag`, `env`, `config`, `default`), пути `profile.json` и `credentials.json` этого профиля, и по каждому полю — его значение, источник (`flag`, `env`, `file`, `default`) и, для сервера, признак «задан»/«не задан» у его секрета — само значение секрета не печатается никогда.

`config --json` SHALL печатать тот же состав структурой в стандартный вывод; диагностика идёт в поток ошибок.

`config init [--profile <профиль>]` SHALL создавать общий файл с полем `profile: "default"`, если его ещё нет, каталог указанного профиля (по умолчанию `default`), файл `profile.json` с умолчаниями и файл `credentials.json` с пустым словарём секретов. Файлы SHALL создаваться эксклюзивно; уже существующие файлы команда MUST NOT изменять. Код завершения SHALL быть 0. Повторный запуск SHALL не менять ни одного файла.

`config use <профиль>` SHALL записывать имя существующего профиля в поле `profile` общего файла. Несуществующий профиль SHALL приводить к ошибке с путём к отсутствующему каталогу профиля.

`config profiles` SHALL печатать список профилей с их полем `description`, отмечая текущий выбранный профиль.

#### Scenario: Просмотр настроек

- **WHEN** выполнено `tt-testops config`
- **THEN** напечатаны путь общего файла, выбранный профиль и способ выбора, пути `profile.json` и `credentials.json`, и по каждому полю — значение и источник

#### Scenario: Просмотр настроек структурой

- **WHEN** выполнено `tt-testops config --json`
- **THEN** в стандартный вывод попадает структура с тем же составом, а диагностика — в поток ошибок

#### Scenario: Секрет виден только как признак

- **WHEN** выполнено `tt-testops config`, а у сервера `testops` задан токен
- **THEN** напечатано, что секрет задан, но не его значение

#### Scenario: Первая инициализация

- **WHEN** выполнено `tt-testops config init`, а `~/.tt-testops/` пуст
- **THEN** созданы общий файл с `profile: "default"`, каталог `profiles/default/`, файл `profile.json` с умолчаниями и файл `credentials.json` с пустым словарём

#### Scenario: Повторная инициализация ничего не меняет

- **WHEN** `tt-testops config init` выполнена дважды подряд
- **THEN** второй запуск не изменяет ни одного файла, код завершения 0

#### Scenario: Переключение профиля

- **WHEN** выполнено `tt-testops config use <профиль>`, а каталог этого профиля существует
- **THEN** поле `profile` общего файла записано этим именем

#### Scenario: Переключение на несуществующий профиль

- **WHEN** выполнено `tt-testops config use <профиль>`, а каталога `profiles/<профиль>/` нет
- **THEN** команда завершается ошибкой с полным путём к отсутствующему каталогу

#### Scenario: Список профилей

- **WHEN** выполнено `tt-testops config profiles`
- **THEN** напечатан список профилей с их описанием, и текущий профиль отмечен
